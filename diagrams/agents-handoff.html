The agent team: who does what, and how work is handed over

One task travels top to bottom. Every agent is a separate sub-agent with one job. The files on the right are the only channel between them.
What every agent is made of (one Markdown file per agent)
1 · IdentityName, role, character, and its place in the pipeline
2 · Hard rulesWhat it must never do, read before everything else
3 · WorkflowIts own numbered steps, from "load memory" to "report"
4 · InputThe task and the exact files it is allowed to read
5 · OutputOne fixed section it writes, in a fixed format
6 · MemoryLong-term facts it reads at start and may add to at the end

Lessons learned, and what is still missing

Version 1Every agent appended its full notes to one task file. The file grew with each stage, and every next agent had to read all of it. That used many tokens and slowed every stage.

Version 2A small main file (task, requirements, one status row with a short summary per stage) plus one detail file per stage. Each agent reads only what its job needs. A fix replaces the old text instead of being added below it.

ExceptionLeo always reads the full implementation detail and the real code. Tokens are never saved at the review.

Open gapUnit tests and API tests for backend changes are developer work, not tester work. They need their own agent between Noah and Leo. The architecture does not have this agent yet; it is the next one to add. End-to-end tests are covered by the separate testing team.

RemovedThe MCP connection to the task board. In the first versions every agent talked to the task board through an MCP server: it read its tasks there and changed the status itself at each stage. It worked, and it made the progress visible. But every agent carried the tool definitions and spent calls on status updates in every run. That wasted tokens, so I removed it: one script reads the task at the start, one writes the result at the end, and the agents work on local files only.

Memory: how an agent gets better without re-reading everything
Agent memoryOne long-term file per agent with facts it learned. Read as step 0 of every run.
Project memory and docsFacts and a summary per project, so an agent knows the project before it opens the code.
Write gateA fact is saved only if it is new, will stay true, and would have changed what the agent did.
